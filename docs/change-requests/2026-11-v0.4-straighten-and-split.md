# PDFMango: "Straighten and split" features

## Golden rule: do not break what already works

PDFMango is live and working. None of this work may change existing behaviour.

- Every new feature is opt-in: it runs only when the user picks it. Defaults are unchanged.
- When the new page fields are at their defaults (`fineRotation = 0`, no `crop`,
  no `corners`), the export path must be exactly the current one. Branch around
  the new code; don't rewrite existing functions.
- Before starting, run the full existing test suite and record the results.
  After each feature, run it again: everything that passed must still pass.
- Add a regression test: export every existing fixture before and after your
  changes and compare page count, page order, /Rotate values and extracted text
  (identical), and file size (within 1%).
- If an existing test or behaviour seems to need changing, stop and ask Venkat
  first. Don't edit existing tests to make them pass.
- Don't upgrade dependencies (including the pinned `mupdf`) as part of this work.
- Add an on/off flag for each new feature in `src/pdfmango.config.ts`, so any one
  can be switched off and redeployed if it causes trouble.

Read spec.md and the current code first. Fit these into the existing
architecture: page model in the main thread, all MuPDF work in the worker.
Each feature must work with undo/redo and show correctly in thumbnails.
Do them in order and commit after each one.

## 1. Auto-straighten a slightly tilted page (lossless)

Goal: fix scans and photos that are tilted by up to ±15°.

- Detect the angle in the worker:
  - Render the page greyscale at about 1000 px wide (re-use the thumbnail render path).
  - Binarise (Otsu), then use a projection profile: for each candidate angle,
    project dark pixels onto rows and score the variance of the row histogram.
  - Search coarse (−15° to +15° in 0.5° steps), then fine (±0.5° in 0.05° steps).
  - If the best score is not clearly better than 0°, or the page has too little
    text or lines, return 0 and leave the page alone. Never "fix" a page wrongly.
- Apply losslessly at export, without re-rasterising: wrap the page content in a
  rotation about the page centre (prepend `q cos sin -sin cos tx ty cm`, append `Q`).
  Text stays selectable; Tamil and other Unicode text is untouched. Keep the page
  size; small corner slivers may be lost at larger angles.
- UI: a "Straighten" action per page and for a selection. A snackbar shows the
  result ("Straightened by 3.4°" or "Already straight").
- Page model: add `fineRotation: number` (degrees, default 0) to PageRef.
  Thumbnails show it with a CSS rotate.
- Put the projection-profile code in its own module; feature 4 re-uses it.
- Config flag: `features.straighten`.

## 2. Manual fine-rotate slider

- In the large page preview: a slider from −10° to +10° in 0.1° steps, plus Reset.
- It writes the same `fineRotation` field and is applied at export as in feature 1.
- Config flag: `features.fineRotate`.

## 3. Straighten photo (manual perspective correction)

Goal: a phone photo of one sheet, taken at an angle, becomes a flat, cropped page.
Image pages only (JPG/PNG added by the user).

- UI: four draggable corner handles (default: inset 5% from the edges), a
  magnifier loupe while dragging on touch screens, and Apply / Cancel.
- Processing in the worker:
  - Try MuPDF.js `Pixmap.prototype.warp(quad, width, height)` first. The docs
    list warp for MuPDF.js; `detectDocument`, `deskew`, `detectSkew` and
    `autowarp` are "only mutool run", so don't use those. Verify warp works in
    our pinned version before building the UI.
  - Fallback: compute the homography from the 4 points and resample (bilinear)
    in plain TypeScript in the worker.
  - Output size = average lengths of opposite edges, long side capped at 3000 px.
    Encode as JPEG quality 90.
  - Keep the original image in memory, so Cancel, Undo and re-editing work.
- Page model: store the corner points on the PageRef (`corners`).
- Config flag: `features.straightenPhoto`.

## 4. Split two-page book spreads into separate pages (automatic, with review)

Goal: a scan or photo of two facing pages becomes two pages, for a whole book in
one go. Manual adjustment is needed only for the few pages the app is unsure about.

### Automatic mode (the main way to use it)

- UI: a toolbar action "Split book spreads". It applies to the selection, or to
  all pages if nothing is selected. It runs in the worker with a progress bar and Cancel.
- For each page, render greyscale at about 800 px wide and decide whether it is a spread.
  All three must be true:
  1. Landscape: width ≥ 1.2 × height (threshold in config).
  2. A clear gutter in the middle band (40–60% of the width). Re-use the
     projection-profile module from feature 1, on columns: the gutter is the
     darkest shadow column or the emptiest column, whichever stands out more.
     Confidence = how far that column stands out from its neighbours (z-score).
  3. Both halves contain content (ink density on each side above a small threshold).
- Slanted spine: find the gutter separately in the top and bottom thirds. If the
  two positions differ by more than 1% of the width:
  - if the page has no `fineRotation` yet, apply feature 1's straightening first,
    then re-detect;
  - otherwise flag the page for review.
- Book-wide consistency: after the first pass, take the median gutter position
  of the confident pages. For pages with weak confidence, use that median instead
  of the noisy local result, and flag them for review.
- Outcome per page:
  - Confident spread: split immediately.
  - Uncertain spread: split using the best guess (or the median), and show a
    small "Check split" badge on the thumbnail.
  - Not a spread: leave alone.
- Summary snackbar: "Split 212 spreads into 424 pages; 4 to check · Review",
  where Review opens only the flagged pages, one after another.
- The whole batch is a single undo step.
- Settings in the dialog (remembered only for the session): overlap 0, 1% or 2%
  each side (default 1%, so letters near the spine aren't cut); "Right page
  first" (default off, for right-to-left books).

### Review and manual mode

- The review screen and the per-page "Split into two pages" action share one
  editor: a draggable vertical split line, the overlap setting, and Apply / Skip /
  "Don't split this page".
- Manual split stays available on any single page.

### Applying the split

- **PDF pages (lossless):** replace the PageRef with two PageRefs pointing at the
  same source page, each with `crop: { x0, y0, x1, y1 }` in normalised coordinates.
  At export, graft the page once per half and set `/CropBox` and `/MediaBox` on
  each copy.
  - Compute crops in the page's unrotated coordinate space, so the visual left
    half is cut correctly on pages with `/Rotate`.
  - If the page has a non-zero `fineRotation`, the crop applies after that rotation.
  - The hidden half stays inside the file. Balanced and Strong compression still
    carry it; the Scan level re-renders and drops it. Mention this in the tooltip.
- **Image pages:** physically crop the pixels with a rectangular MuPDF `warp`
  (the same call as feature 3), so the hidden half is truly gone.
- Thumbnails render only the cropped region; page numbers update automatically.

### Config (in `src/pdfmango.config.ts`)

`features.splitSpreads` (on/off), `split.minAspect: 1.2`,
`split.middleBand: [0.4, 0.6]`, `split.minConfidence` (tune on the fixtures),
`split.defaultOverlap: 0.01`.

## Tests and acceptance (this round)

### Fixtures (add to `tests/fixtures/`)

- Scanned pages tilted +2°, +5° and −8°
- A page with no text (a photo)
- A Tamil text PDF page tilted 3°
- A phone photo of a single sheet shot at an angle
- A two-page book spread, as a PDF scan and as a JPG
- A spread on a page with /Rotate 90
- A 20-page book scan PDF mixing spreads and single pages (including a cover)
- A phone-photo spread with a slightly slanted spine
- A spread with a dark gutter shadow, and one with a white gap

### Unit tests (Vitest)

- The angle detector recovers the known angles within ±0.2°; the no-text page returns 0.
- The gutter detector finds the spine within 2% of the width on the spread fixtures.
- Spread detection: all spreads detected; no single page or cover split;
  uncertain pages flagged rather than wrongly split.
- Rotation-matrix and crop-box maths, including /Rotate 90.
- Undo/redo of `fineRotation`, `corners` and `crop`; one undo reverses a whole batch split.

### End-to-end tests (Playwright)

- Straighten → export → reopen: page count unchanged, and the Tamil page's text is
  still selectable and identical when copied.
- Split → export: each spread becomes two pages in the right order, with text
  selectable on each.
- Batch split on the 20-page book: correct page count, flagged pages shown in Review.

### Acceptance

- The regression test from the golden rule passes on every existing fixture.
- The angle search for one page takes under 1 second on a mid-range laptop.
- A 300-page book batch split completes in under a minute on a mid-range laptop.
- Update spec.md, README (Features), the About page (How to use) and CHANGELOG.md.

## Deferred: flatten curved book pages with UVDoc

Do NOT start this unless Venkat explicitly asks for it in a later session.
When he does, the golden rule above still applies.

### Step 1: spike (decide before building)

- Compare two open-weight models on 15–20 of Venkat's own phone photos of Tamil
  book pages:
  - UVDoc: MIT licence. Use the ONNX export from PaddleOCR (about 31 MB).
  - Flattener (DevWorld/flattener on Hugging Face): Apache-2.0. Dewarp, page
    detection and orientation models; its repo has browser export tools. Trained
    on Korean and English pages, so Tamil must be tested.
- Also check whether Flattener's page-detection model can find the two pages in a
  spread directly, and compare it with feature 4's gutter detection on the same photos.
- Measure for each:
  - Quality: lines of text straight, nothing cut off, letters not smeared.
  - Time per page on a mid-range laptop and a mid-range Android phone.
  - Peak memory and download size.
- Write SPIKE-DEWARP.md with sample before/after images and timings, then stop
  for Venkat's decision.

### Step 2: build (after Venkat chooses a model)

- Runtime: `onnxruntime-web` (MIT), in its own dedicated worker. Use the WebGPU
  backend, falling back to WASM.
- Model hosting: commit the .onnx file to the repo under `public/models/`. Don't
  use Git LFS, because GitHub Pages serves LFS pointers, not the files. A ~31 MB
  file is under GitHub's 100 MB file limit.
- Loading:
  - Only when the user first taps "Flatten book page".
  - Before downloading, say so once: "This downloads a 31 MB model, one time only."
  - Show download progress, then cache the model with the service worker for
    offline use. Nobody else ever downloads it.
- Pipeline for each page:
  1. Straighten (feature 1) and split (feature 4) first. The model expects a single page.
  2. Resize the image to the model's input size (read it from the model's config).
  3. Run the model to get a coarse correction grid.
  4. Upsample the grid (bilinear) to full resolution.
  5. Grid-sample the original full-resolution image, not the resized one, so
     the text stays sharp.
  6. Encode as JPEG quality 90 and replace the image page. Keep the original for Undo.
- Batch use: "Flatten book pages" applies to the selection, with per-page
  progress and Cancel, and is a single undo step.
- PDF pages: render at 200 ppi, flatten, then replace the page with the image. If
  the page has real (selectable) text, warn that the text will become an image.
  For true scans this changes nothing.
- A clear message if the device runs out of memory; the app stays usable.
- Config flag: `features.flattenBook` (default false until tested on real devices).
- Licence: add the model's licence and citation to THIRD_PARTY_NOTICES.md and the
  About page credits.
- Acceptance: on the spike photos, text lines near the spine come out visibly
  straighter. Time per page is within what the spike measured. Existing features
  are unaffected (golden rule tests pass).
